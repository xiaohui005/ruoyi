# 股票分析与提醒系统开发完整流程

## 1. 文档定位

本文档用于把本次交流中已经确认的需求、边界、技术路线、实施顺序和交付标准，收敛成一份统一的开发流程入口。

适用对象：

1. 你自己继续开发时的执行入口
2. 后续接手该项目的其他开发人员
3. 未来再次让 Codex 继续实现该系统时的统一上下文

## 2. 本次交流沉淀下来的固定结论

本项目后续开发必须默认以下结论成立：

1. 项目基于当前 `ruoyi-vue-pro / yudao` 仓库落地，不另起一套独立前后端工程
2. 业务模块独立命名为 `stock`，不混入系统自带 `system` 业务模块
3. 第一阶段就要走真实数据主链路，不采用“长期 Mock 驱动生产功能”的方案
4. `Mock/CSV` 只保留给测试、联调、演示、样例复现和排障
5. 关注股票必须支持专门登记、专门采集、专门分析、专门提醒
6. 免费数据源先跑通，付费数据源接口必须预留，避免后续重构成本过高
7. 所有规则必须按“市场节点 -> 量价分析 -> 做T执行”的过滤链输出建议
8. 前端必须明确展示规则判断过程，而不是只返回一个黑盒结论

## 4. 总体开发原则

### 4.1 技术原则

1. 保持当前仓库技术栈，不另起炉灶
2. 后端规则全部集中在服务层实现
3. 前端只做配置、查询、展示、确认，不承载交易规则核心判断
4. 数据源通过 Provider/SPI 抽象，不写死到单一供应商
5. 所有第三方能力通过扩展实现，不魔改框架核心

### 4.2 业务原则

1. 六大节点是交易入口判断，不是可选模块
2. 量价分析是标的筛选层，不可绕过
3. 做T分析只对满足条件的低位结构股输出
4. 一旦结构失效，系统必须主动输出风险提示
5. 系统仅做辅助分析，不做自动下单

### 4.3 交付原则

1. 先打通最小闭环，再逐步增强体验
2. 先后端、后前端，先真实链路、后图表增强
3. 每个阶段都必须有可验证结果
4. 文档、部署、使用说明要与实现同步更新

## 5. 开发全流程

## 5.1 阶段 0：冻结范围与约束

开工前先冻结以下内容：

1. 第一阶段只做分析、监控、提醒、复盘，不做自动交易
2. 前端页面范围固定为：
   - 市场节点页
   - 股票分析页
   - 行情监控页
   - 自选股监控页
   - 提醒设置页
   - 历史记录页
3. 生产环境必须使用真实数据源
4. 关注股票必须具备专采能力

输出物：

1. 需求冻结说明
2. 本文档和设计文档确认版

## 5.2 阶段 1：模块骨架与数据库落地

目标：

1. 创建独立后端模块 `yudao-module-stock`
2. 创建前端独立业务目录 `src/api/stock`、`src/views/stock`
3. 建立股票业务核心数据表

最低交付：

1. 模块能编译
2. 建表 SQL 可执行
3. DO / Mapper / 基础枚举完成骨架

重点表建议优先顺序：

1. `stock_watchlist`
2. `stock_analysis_config`
3. `stock_analysis_record`
4. `stock_t_strategy_record`
5. `stock_alert_rule`
6. `stock_alert_record`
7. `stock_market_snapshot`
8. `stock_kline_daily`

## 5.3 阶段 2：真实数据链路接入

目标：

1. 接入免费真实数据源组合
2. 建立主源、补源、回填源、测试源分层
3. 让行情数据可以落库、缓存、复用

推荐策略：

1. 主源：`Tushare HTTP`
2. 补源：`AKTools HTTP`
3. 历史回填：`BaoStock`
4. 测试/样例：`Mock/CSV`

必须说明：

1. `Tushare` 属于“免费起步，可平滑升级付费”的路线
2. `AKTools` 属于免费补源方案
3. `BaoStock` 更适合历史回填，不适合作为盘中主链路
4. `Mock/CSV` 不作为正式生产模式

这一步完成标准：

1. 能拉取真实股票日线
2. 能拉取市场概览
3. 能把关键数据落到数据库或缓存
4. 主源失败时有补源或缓存回退策略

## 5.4 阶段 3：规则引擎开发

目标：

1. 落地六大市场节点识别
2. 落地量价分析规则
3. 落地三重底做T规则
4. 输出统一分析结论

固定执行顺序：

1. 先做市场节点引擎
2. 再做量价分析引擎
3. 最后做做T引擎

禁止做法：

1. 不允许跳过市场节点直接给做T建议
2. 不允许只输出“买/卖”而没有原因说明

输出结果至少包含：

1. 当前市场节点
2. 量价类型
3. 股价位置
4. 是否适合做T
5. 支撑位
6. 压力位
7. 建议仓位
8. 结构失效条件
9. 风险等级
10. 原因说明

## 5.5 阶段 4：关注股专采与提醒闭环

这是本项目非常关键的一步，不能只停留在“临时查询”。

必须具备：

1. 用户能把股票加入监控池
2. 每只股票能配置采集级别
3. 每只股票能配置采集周期
4. 每只股票能单独决定是否启用量价分析、做T分析、价格提醒、信号提醒
5. 系统能记录最近采集、最近分析、最近提醒状态

建议采集级别：

1. `NORMAL`
2. `KEY`
3. `CORE`

建议调度拆分：

1. 市场快照采集任务
2. 自选股行情采集任务
3. 自选股分析任务
4. 提醒发送任务
5. 历史回填任务

## 5.6 阶段 5：前端页面落地

前端不是只做一个查询框，而是要把规则链展示清楚。

页面职责建议如下：

1. 市场节点页
说明：展示当前市场节点、可交易状态、市场概览、历史节点记录

2. 股票分析页
说明：输入股票代码后，展示市场节点适配、量价结论、做T结论，并支持一键加入监控

3. 行情监控页
说明：展示 K 线、成交量、支撑位、压力位、三重底标记、提醒时间轴

4. 自选股监控页
说明：展示关注股列表、采集级别、监控状态、最近分析和最近提醒

5. 提醒设置页
说明：配置提醒渠道、提醒规则、测试发送

6. 历史记录页
说明：查看分析记录、提醒记录、交易记录

前端展示重点必须固定：

1. 先展示“当前是否处于可交易窗口”
2. 再展示“量价结构是否支持”
3. 最后展示“做T是否成立以及关键价位”

## 7. 数据源说明

## 7.1 免费源

优先推荐：

1. `Tushare HTTP`
说明：免费起步，后续可付费升级，适合作为主源

2. `AKTools HTTP`
说明：免费补源，适合作为市场概览、板块、补字段来源

3. `BaoStock`
说明：免费历史回填源，适合作为导入辅助

## 7.2 付费源预留

后续建议预留：

1. `Tushare Pro` 高权限方案
2. `JQData`
3. `Wind`
4. `iFinD`

设计要求：

1. 接口抽象先行
2. 主流程不依赖某一家厂商的返回格式
3. DTO 归一化后再进入规则层

## 7.3 Mock 的定位

必须写死说明：

1. Mock 只用于测试
2. CSV 只用于测试样例、历史回放、排障
3. 正式环境分析结果不得来自 Mock 数据
